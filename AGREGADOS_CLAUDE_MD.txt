## Self-Verification Loop (OBLIGATORIO — NO NEGOCIABLE)

### Cuándo ejecutar verificación

Después de CADA uno de estos eventos:
- Modificar cualquier archivo en `/executor/`
- Modificar cualquier archivo en `/mobile_ui/`
- Modificar cualquier schema o contrato (freeze o no-freeze)
- Crear o modificar expected outputs
- Agregar nueva funcionalidad
- Corregir un bug
- Antes de declarar una tarea como "completada"

### Proceso de verificación (AUTOMÁTICO)

1. **Leer** `VERIFICATION_CHECKLIST.md` completo
2. **Ejecutar** todos los tests de las secciones "Functional Tests" y "Execution Tests"
3. **Verificar** cada checkbox de cada sección
4. **Reportar** el resultado AL USUARIO en el formato especificado
5. **Si algo falla:** corregir, volver a verificar, y solo entonces continuar

### Formato del reporte (OBLIGATORIO)

```
🔍 VERIFICACIÓN COMPLETADA — [timestamp]

Secciones verificadas: X/10
Checks pasados: X/Y

❌ FALLOS DETECTADOS: (si los hay)
  [lista de fallos]

✅ CORRECCIONES APLICADAS: (si corresponde)
  [lista de correcciones]

🔄 RE-VERIFICACIÓN: (si hubo correcciones)
  Checks pasados: X/Y ✅

Estado: [LISTO PARA CONTINUAR | REQUIERE ATENCIÓN | BLOQUEADO]
```

### Reglas críticas de verificación

**REGLA 1:** Si cualquier check falla, NO continúes con el siguiente cambio. Primero corrige el fallo, vuelve a verificar, y solo entonces procede.

**REGLA 2:** No pidas permiso al usuario para verificar. La verificación es automática y obligatoria.

**REGLA 3:** Si un check falla 3 veces consecutivas después de intentar corregirlo, DETENTE y pregúntale al usuario cómo proceder.

**REGLA 4:** Los archivos en `/freeze/v1/` NUNCA deben modificarse. Si un check indica que algo en freeze debe cambiar, el problema está en otro archivo (executor, schema no-freeze, expected output), NO en freeze.

**REGLA 5:** Si detectas un bug durante la verificación, corrígelo ANTES de reportar "verificación completada".

### Excepciones (las ÚNICAS)

La verificación se puede OMITIR solo si el usuario dice explícitamente:
- "Skip verification"
- "Sin verificar"
- "Omite la verificación esta vez"

En todos los demás casos, la verificación es OBLIGATORIA.

### Bug Detection — Qué buscar activamente

Durante la verificación, busca activamente estos bugs comunes:

**Python:**
- IndentationError
- Variables undefined
- Imports que no existen
- Funciones llamadas antes de ser definidas
- Tipos inconsistentes (retornar dict en vez de list)
- Loops infinitos
- Condiciones siempre True/False

**JSON:**
- Comas faltantes o extras
- Llaves/corchetes sin cerrar
- Comillas mal escapadas
- Tipos incorrectos (string en vez de array)

**Lógica:**
- Validadores que no validan lo correcto
- Clasificadores que siempre retornan el mismo valor
- Datos que se pierden entre funciones
- Cursos que se mezclan entre sí

**Frontend:**
- Event listeners no asignados
- Fetch sin URL válida
- Promesas sin .catch()
- Formularios sin validación

### Prioridad de corrección

Si detectas múltiples fallos, corrígelos en este orden:
1. **Críticos** — Syntax errors que impiden ejecución
2. **Altos** — Inconsistencias con freeze (contrato/schema)
3. **Medios** — Bugs lógicos que producen output incorrecto
4. **Bajos** — Mejoras de código o warnings

### Validación de correcciones

Después de corregir un fallo:
1. Vuelve a ejecutar el check específico que falló
2. Ejecuta los checks de secciones relacionadas
3. Solo si todos pasan, continúa

---

## Debugging Protocol

Si durante la verificación detectas comportamiento inesperado:

1. **Identifica** qué check falló y por qué
2. **Aísla** el problema (¿es Python, JSON, lógica, frontend?)
3. **Reproduce** el error de forma mínima
4. **Corrige** el problema específico
5. **Verifica** que la corrección no rompió otra cosa
6. **Reporta** qué se corrigió y por qué

---

## Continuous Validation Mindset

No pienses en la verificación como un paso extra. Piensa en ella como parte integral del desarrollo:

- Cada cambio → verificación automática
- Cada verificación → oportunidad de detectar bugs temprano
- Cada bug detectado temprano → tiempo ahorrado más adelante

La verificación NO es opcional. Es el mecanismo que garantiza que el sistema evoluciona sin colapsar.
