# ON_PARSER_BEHAVIOR_TESTS_HARDENING

OBJETIVO

Construir un hardened extension layer para:

PARSER_BEHAVIOR_TESTS_v1.md

El objetivo NO es reescribir completamente el archivo.

El objetivo es:
- endurecer determinismo
- endurecer resiliencia semántica
- endurecer estabilidad longitudinal
- endurecer contract compliance
- endurecer fallback safety
- endurecer ambiguity handling
- endurecer malformed-input resilience

El hardening debe orientarse a:
semantic-operational stability under chaotic real-world input.

---

CONTEXTO OBLIGATORIO

El hardening debe respetar completamente:

- PARSER_v1_SPEC_FREEZE
- PARSER_OUTPUT_CONTRACT_v1_FREEZE
- SRP_SCHEMA_v3
- PARSER_BEHAVIOR_TESTS_v1

El hardening debe asumir:
- inputs orales transcritos
- multicurso
- narración fragmentada
- referencias ambiguas
- puntuación rota
- texto mal formado
- continuidad interrumpida
- ruido semántico
- drift narrativo
- ambigüedad contextual

---

OBJETIVO TÉCNICO CENTRAL

Blindar el comportamiento determinista del parser frente a:
- entropía informativa
- redistribución insegura
- sobreinferencia compuesta
- colapso de chunking
- drift semántico
- ambigüedad longitudinal
- malformed inputs
- persistencia incorrecta
- category contamination

---

NUEVAS FAMILIAS DE TESTS OBLIGATORIAS

El hardening debe agregar nuevas familias de tests.

NO reemplazar familias existentes.

---

1. DETERMINISM EQUIVALENCE TESTS

Validar:
- equivalencia semántica
- estabilidad de persistencia
- estabilidad de categorías
- estabilidad longitudinal

Inputs equivalentes semánticamente deben producir:
- continuidad equivalente
- persistencia equivalente
- clasificación equivalente

---

2. SCHEMA INTEGRITY TESTS

Validar:
- una sola categoría primaria
- ausencia de estructuras huérfanas
- ausencia de referencias cruzadas inválidas
- integridad estructural
- compatibilidad contract-safe

Validar:
- preservación de invariantes del schema
- compatibilidad con parser output contract

---

3. COMPOUND OVERINFERENCE TESTS

Validar:
- acumulación de frases ambiguas
- múltiples señales débiles
- inferencia compuesta accidental

El parser MUST NOT:
- construir proyectos inexistentes
- derivar continuidad no explícita
- construir estrategias complejas desde hints débiles

---

4. PARTIAL COLLAPSE RECOVERY TESTS

Validar resiliencia frente a:
- chunking roto
- multicurso incompleto
- frases truncadas
- referencias inconclusas
- narración colapsada

El parser debe:
- preservar estructura parcial segura
- evitar colapso global
- evitar alucinación estructural

---

5. PRONOUN AMBIGUITY TESTS

Validar:
- referencias ambiguas
- pronombres sin referente
- continuidad incompleta

El parser MUST:
- preservar ambigüedad
- evitar inventar referentes

---

6. LONGITUDINAL RECONCILIATION TESTS

Validar:
- evolución temporal
- progresión pedagógica
- reconciliación de estados longitudinales

Ejemplo:
- “todavía no logran”
→ posteriormente:
- “ya lograron”

El parser debe:
- tolerar evolución
- evitar contradicción rígida
- evitar duplicación conflictiva

---

7. CHUNK REASSEMBLY TESTS

Validar:
- continuidad separada por distancia textual
- reconexión contextual
- continuidad multicapa

El parser debe:
- reconectar continuidad legítima
- evitar reconexión agresiva

---

8. MALFORMED INPUT TESTS

Validar resiliencia frente a:
- puntuación ausente
- markdown roto
- palabras fusionadas
- listas incompletas
- oralidad extrema
- ruido transcripcional

El parser debe:
- preservar operatividad
- evitar colapso semántico
- evitar autocorrección destructiva

---

9. CONTRACT COMPLIANCE TESTS

Validar:
- cumplimiento estricto del output contract
- categorías válidas
- continuidad válida
- ambigüedad explícita
- shape-safe output

El parser MUST NOT:
- generar estructuras inválidas
- producir categorías ilegales
- producir persistencia incompatible

---

10. CRITICAL PERSISTENCE SURVIVAL TESTS

Validar:
- preservación de continuidad crítica
- supervivencia de recordatorios importantes
- estabilidad de pendientes operacionales

Redistribución NO debe destruir:
- evaluaciones
- materiales críticos
- continuidad inmediata importante

---

11. CLEANER / NORMALIZATION TESTS

Validar:
- limpieza segura
- normalización mínima
- preservación semántica
- resiliencia textual

El parser MUST NOT:
- normalizar destructivamente
- autocorregir agresivamente
- alterar intención semántica

---

RESTRICCIONES

El hardening NO debe:
- introducir implementación
- introducir pseudocódigo
- introducir runtime architecture
- introducir rendering logic

El hardening SÍ debe:
- fortalecer garantías semánticas
- fortalecer determinismo
- fortalecer resiliencia operacional
- fortalecer contract safety

---

REGLA CENTRAL

El hardening debe priorizar:

semantic-operational stability under noisy input

por sobre:
- simplificación
- limpieza superficial
- reinterpretación agresiva
- completitud artificial
